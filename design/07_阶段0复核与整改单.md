### 1.2 部署机制描述：结论对，理由错（必须纠正认知）

CodeBuddy 说「Pages 部署走 `dist/` artifact（`.gitignore` 注明源在 `ui/` + `scripts/build_ui.mjs`）」——**这不是当前机制**。真实 `.github/workflows/deploy-pages.yml`：

```
actions/checkout@v4 (ref: main)
  → npm run build:bundle（continue-on-error，失败回退已提交 bundle.js）
  → mkdir site/；按固定白名单 cp 根 web 面 → site/
  → cp -r src/. site/src/  +  cp -r data/. site/data/
  → sed 注入 CACHE_VERSION = 'v2-<sha7>' 到 site/sw.js
  → actions/upload-pages-artifact@v3 (path: site)
  → actions/deploy-pages@v4
```

`.gitignore` 第 6 行那句「dist/ 部署走 Pages artifact，源在 ui/ + scripts/build_ui.mjs」是 **2026-10-06 部署治理收口前**描述 `daily.yml` 旧 dist 通道的历史注释（workflow 头 1–31 行明确写了双通道互相覆盖的根因与收口）。

`design/` 不会上线的**真实原因**是两条：① `on:push.paths` 白名单不含 `design/**` → 提交不触发部署；② 产物组装是**固定清单 cp**，不含 `design/` → 即便触发也不会进 `site/`。反过来要警惕：白名单里 `src/**` 是通配递归，原型文件**放进 `src/` 就会被带上线上**。

### 3.2 给多选择器列表逐项加作用域前缀（P0，最高优先）

`s-selfcheck.js` 与 `design/05_落地实施与验收.md` 5.1 的脚本**同步改**。新增一个 helper，两个检测函数都走它：

```js
function scoped(sel) {
  return sel.split(",").map(function (s) { return ".s-scope " + s.trim(); }).join(", ");
}

// checkTouchTargets 内：
var sel = "button, a[href], input, select, textarea, summary, [role='tab'], [role='button'], [tabindex='0']";
Array.prototype.forEach.call(document.querySelectorAll(scoped(sel)), function (el) { /* 原逻辑 */ });

// checkContrast 内同理：
var sel2 = ".s-kpi__label, .s-kpi__value, .s-card__title, .s-section__title, .s-verdict__text, .s-btn, .s-table th, .s-table td, .s-ticker__item, .s-prose p, .s-badge";
Array.prototype.forEach.call(document.querySelectorAll(scoped(sel2)), function (el) { /* 原逻辑 */ });
```

修完在阶段 0 页面上验：`S.runSelfTest().touchTargets.checked === 0`、`contrast.checked === 0`。**注意：此时 `report.pass` 仍应为 false**（见 3.5），不要把「checked=0」当成整体通过。
