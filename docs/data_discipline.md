四条纪律：一、二来自真实事故；三来自真实事故（已补救，但机制未修）；
四来自推演风险（**尚未实证，写下来是因为发生过一次疑似**）。
改之前请先读对应的事故。

## 纪律一：「一致率 100%」必须先证伪同源，否则是自证循环

### 条款

任何"两源互相验证"的结论，在采信前**必须先确认两个源的上游是真正独立的**。
一致率高不等于冗余度高——**如果两者取的是同一个端点，100% 是必然结果，是零信息量的自证**。

### 判定步骤（做对账时必须逐条走过）

1. **找到两个源的实现**，读到发请求的那一行为止（不是读文档，是读**源码/实际 URL**）
2. **比对 URL / 端点 / 上游供应商**：相同 → 判为**同源**，不算独立验证
3. 不同供应商，但**其中一家是另一家的封装/转发**（常见于 AkShare 这类聚合库封装券商接口）→ 同样判同源
4. 确认真独立后，一致率才有意义

### 事故：涨停池"备源"其实是主源（2026-10-11 发现）

`docs/ztpool_fallback_plan.md` 曾写着：

> 东财 vs AkShare 名单一致率 **100%**（69/69）… → AkShare `zt_pool` 已取得"等价备源"资格

读了源码才发现：

```
akshare/stock_feature/stock_ztb_em.py:33
url = "https://push2ex.eastmoney.com/getTopicZTPool"
```

**与主源 URL 一字不差**——AkShare 不是第二家数据源，是同一个东财端点的另一个客户端。
四项 100% 是同一份数据查两次的结果。

后果：降级链 ①② 实为单点，`push2ex` 一挂两层同时失效。
**2026-08-14~09-03 那 14 天"主源与备源均失败"正是此因——不是运气差，是它们本来就是一个东西。**

真正的独立观测是 `market_data.derive_zt_from_snapshot()`（自有快照 + 涨跌幅公式自建，
上游与东财无关）。

## 纪律二：对账源 ≠ 备源——口径不同的只能比对，不能互换

### 条款

一个源若与主源**口径不同**（统计范围、标的范围、时点、单位任一不同），它只能当
**对账源**（比对差异、发现异常），**绝不能当备源**（顶替缺失值进历史序列）。

理由：顶替会让历史序列出现**静默口径跳变**——
缺席时下游拒收并显示"缺席"（**可见**），混入异口径则是污染分位与统计（**不可见**）。
宁缺毋假。

### 判定步骤

1. 问：这个源的**统计范围**和主源一样吗？
   （例：legu 统计全 A 约 5224 只含北交所；快照派生只数沪深 A 3558 只——**不一样**）
2. 不一样 → 记 `caliber` 字段写明差异，**只比对，不顶替**
3. 比对时也要**只比可比的部分**：跨口径比绝对值毫无意义，可比的是
   **方向**（涨跌谁多）与**占比**（相对分布）
4. 涉及标的范围差异时（如东财池含北交所、自建池不含），
   差异计算要**先剔除不可比部分**，否则就是假告警

### 事故/应用

- **涨跌家数**：`market_data.fetch_breadth_cross()`（legu 全 A）与
  `derive_breadth()`（沪深 A）口径不同 → 每天各记一份做比对（见
  `src/ztpool_crosscheck.js` 的 `breadthCrosscheck`：只比方向与占比，不比绝对值）。
  2026-09-04~09-24 那 16 天 gapB 缺口**不拿 legu 补**。
- **自建涨停池**：上游与东财无关（够独立），但**字段不全**（无 `fbt`/`fund`/`zb`/`lbc`）
  → 同样只能对账，不进降级链。
  ⇒ **独立性够 ≠ 能当备源**，还要看字段齐不齐。

## 纪律三：跳过的判据是「上一交易日有没有档」，不是「今天是不是交易日」

### 条款

跑批任务在非交易日跳过前，**必须先确认上一交易日已经入档**。
只看"今天是不是交易日"就跳过，等于把补跑的唯一窗口让给日历。

理由：主源（`push2ex` 等东财端点）只返回**最近一个交易日**的数据。
某天盘后跑失败 → 次日开盘后源已切到新交易日，**旧交易日的数据再也取不回来**——
这不是"晚一天补"，是**永久缺失**。

### 判定步骤（跑批调度必须逐条走过）

1. 非交易日（周末/节假日）触发时，**不要直接 return**
2. 查 `archive-index.latestDate`（或 `data/archive.json` 末档）：
   上一个**交易日**是否已入档
3. 未入档 → **照常补跑**（源此时返回的仍是那个未入档的交易日，正是要补的）
4. 已入档 → 才跳过

### 事故：10-09 险些永久缺失（2026-10-12 发现，已补救）

- 10-09（周五）盘后主跑**没成功**（报告目录只有 `intraday_2026-10-09`，
  没有 `post_market_2026-10-09`），档停在 10-08。
- 10-10（周六）跑批判定"非交易日"→ **直接跳过**，10-09 无人补。
- 10-12（周一）开盘前检查才发现。此时距源切到 10-12 只剩几小时——
  若不是那次检查，**10-09 就是永久缺口**。

补跑窗口只有「下一交易日开盘前」这一小段：源一旦切走，数据不可逆。
**2026 年至今缺天台账只缺 10-09 这一天，是运气，不是机制。**

## 纪律四：在档 ≠ 有数据——零值档必须视同缺档

### 条款

缺档检测不能只查"这一天在不在档"，还要查"这一天的核心字段是不是空的"。
一条 `up_count == 0 && zt_count == 0` 的记录，对下游来说和缺档没有区别——
**它让曲线看起来连续，实际是空壳**。

### 判定步骤

1. 检测缺档时，除"日期是否在档"，追加判据：
   核心情绪字段（`up_count` / `zt_count`）**全为零 → 判为伪在档**
2. 伪在档在台账里与缺档**同等对待**（计入 missing，触发补跑/告警）
3. **禁止**用零值填充历史序列——在核字段上，零不是"市场很冷"，是"没取到"

### 风险形态（推演，尚未实证）

本条**没有实证事故**，是 2026-10-12 检查时推演出的风险，记在这里因为
**发生过一次疑似**：

- 10-12 开盘前检查一度判定"10-08 是空壳"（缺天台账显示 `up 0 ≠ 对照 1654`）。
- 复核后**排除**：那是**对照侧**为 0，档案里 10-08 的
  `up_count=1654 / down_count=3516` 是有值的。
- 但推演本身仍成立：现有检测**确实只看日期在不在档**，不验内容。
  一旦某天真的抓到空壳，它会**静默通过**所有缺档检查。

⇒ 这条若真发生，比真缺一天更危险：**缺一天看得见，空壳看不出来**。

## 附：新增数据源时的自检清单

- [ ] 读源码确认 URL/上游，**不是同源**（纪律一）
- [ ] 与主源口径是否一致？不一致 → 标 `caliber`，定位为**对账源**（纪律二）
- [ ] 字段是否齐全？不齐 → 不能进降级链
- [ ] 落盘时带 `source` + `caliber` 注记（下游要知道自己用的是什么）
- [ ] 差异化告警阈值是否**用真实数据标定**过？没标定的阈值要写"待标定"，不许拍脑袋当事实用
- [ ] 跑批跳过前查的是"上一交易日是否在档"还是"今天是不是交易日"？后者会让跑失败的日子**永久缺失**（纪律三）
- [ ] 缺档检测验不验内容？只验日期 → 零值空壳会**静默通过**所有检查（纪律四）
