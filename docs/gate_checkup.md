# 自动建仓全链路闸门体检（Gate Checkup）

> **本脚本只读回放，不修改任何交易决策**；用于区分**【数据覆盖率瓶颈】** vs **【策略闸门过严】**。
> 脚本：`scripts/gate_checkup.mjs` ｜ 入口：`npm run checkup`

## 为什么要有这个脚本

2026-11-05 排查「模拟盘长期 0 成交」时，逐层拆了 `openGapFilterPct`、涨停池一字过滤、
GLM 买前闸、主线题材强度口径——每拆一层才冒出下一层，效率极低。一次性输出全链路漏斗后
才发现：**总闸是 `batchSubmit` 里的 `bucket !== 'main' → 拒单`**，而 93.3% 的候选根本没有
席位明细，`filterOne` 的准入③④因此恒为 `unmet`。

结论：**「字段 null 导致条件不满足」不能等同于「策略闸门过严」**。二者混淆，会把数据缺失
误判成策略失效，进而去错误地放宽风控阈值。以后每次迭代闸门、切换数据源，重跑本脚本即可
直接看到「通过率掉在哪一层、是缺数据还是真过严」。

## 用法

```bash
npm run checkup                              # 全档案回放 + 写归档日志
node scripts/gate_checkup.mjs --no-log        # 只打印，不落盘（只读中的只读）
node scripts/gate_checkup.mjs --recent 20     # 只看最近 20 个交易日（快速体检）
```

EOD 跑完 `paper_daily` 后执行任一命令即可一键体检。**默认不自动挂进 `pi_build.sh`**——
体检是诊断工具，不进交易主链路；需要常态化时由运维/CI 显式调用。

### 落盘范围

| 文件 | 说明 |
|---|---|
| `data/reports/gate_checkup_latest.json` | 最近一次结论（含三张表文本 + 结构化数据 + 逐日明细） |
| `data/reports/gate_checkup_<交易日>.json` | 按交易日存档，同日重跑覆盖 |

两者均为**可重建产物**，已入 `.gitignore`，不进仓库以免 `git status` 长期挂脏。
脚本**不写**账户、配置、选股结果、归档主档等任何生产数据。

## 固定输出：三张表

1. **完整漏斗层级通过率**：交易日链（情绪档 `allowNew` / regime 盖帽）与票次链
   （全候选 → `isAdmissible` → `recommendPicks` → 行情 → GLM → `filterOne main` → 可提交）
   分开列，各自标注分母，避免口径混用。
2. **准入条件三分统计**：`null 数据缺失` / `有值不达标` / `达标`，外加席位明细覆盖率、
   `main_theme` 覆盖、强制剔除命中、数据不足留痕跳过、`watch` 归因。
   **解读原则：先看 null 缺失占比**——高缺失说明是数据覆盖率瓶颈，不是策略闸门过严。
3. **敏感度对照 A/B/C/D**：模拟放行结果（可下单交易日数 / 可提交票次），**纯内存模拟，
   不触碰 `src/lhbfilter.js`**。

| 方案 | 含义 |
|---|---|
| A | 现状，必须 `bucket=main` |
| B | 旁路整道 `filterOne`（**拆掉龙虎资金风控，仅作对照，不采纳**） |
| C | 口径修正：准入「字段 null」不计入 `unmet`，保留强制剔除与降级 |
| D | 仅放开 `netOutflow` 降级，准入仍须全满足 |

### 基线一：回填前（2026-11-05 体检，全档案 258 交易日）

| 方案 | 可下单天数 | 票次 |
|---|---|---|
| A 现状 | 2 (0.8%) | 2 |
| B 旁路 | 232 (89.9%) | 522 |
| **C 口径修正** | **163 (63.2%)** | **288** |
| D 仅放开降级 | 2 (0.8%) | 2 |

表 2 同时记录：`③前三集中度` 与 `④机构/北向净买` 各 **93.3% 为 null**，席位明细覆盖仅
**6.7%**（1388/20625），且只有 **20/258 个交易日**有席位明细（集中在 2026-09-28 之后）；
`LOCKUP_RATIO` / `GAIN_60D` 两条规则 100% 留痕跳过（存档物理上算不出）。

### 基线二：席位明细回填后（2026-11-05，同档案同脚本）

历史席位明细已由 `backfill_seat_details.mjs` 分 8 批全部回补（238 天，约 1 小时，
每批 commit+push 防 EOD reset）。覆盖率 **6.7% → 90.2%**（258/258 天全有 v2 双侧明细）：

| 指标 | 回填前 | 回填后 |
|---|---|---|
| ③③④ null 缺失 | 93.3% | **9.8%** |
| ③ 达标 / 不达标 | 4.4% / 2.4% | **59.2% / 31.0%**（真实分布） |
| ④ 达标 / 不达标 | 2.8% / 3.9% | **39.8% / 50.4%**（真实分布） |
| `bucket=main`（全候选口径） | 38 (0.2%) | **819 (4.0%)** |
| **A 现状真实可提交** | **2 (0.8%) / 2 票次** | **81 天 (31.4%) / 105 票次** |

**方案 C 评估结论（第 5 步）**：回填后 **A = C = D（81 天 / 105 票次，完全一致）**——
C、D 对放行量**零增量**。卡点已从「数据缺失」彻底转为「真实策略判定」（③31% 有值
不达标、④50.4% 有值不达标、netOutflow 降级 13289 票次），这正是策略本来的样子。

因此 **方案 C 无需急于落地**：当前没有收益；按「兜底防御」定位，可在数据源真出现
失效（null 回升）时再启用，或作为低成本防御层随时补上。落地前以本脚本表 2 的
null 占比作为触发指标（>30% 时建议启用）。

## 两步执行顺序（当前状态：第一步已完成）

### 第一步 ✅ 固化体检能力（2026-11-05）

`scripts/gate_checkup.mjs` 入库 + `npm run checkup` 入口 + 本文档。**不改任何策略代码**。
理由：先有常态化校验抓手，以后每次迭代闸门、换数据源都能自动输出这张漏斗通过率表，
避免下次再踩「数据缺失误判成策略失效」的坑。

### 第二步 ⏸ 方案 C：已评估，暂不落地（2026-11-05 回填后结论）

> 本次归因核心是「**null 缺数据 ≠ 条件不满足**」，不是阈值、不是主线强度、不是情绪双闸的
> 风控标准有问题。方案 C 属于**口径修正，不是放宽风控**，性质上与 B 那种直接旁路
> `filterOne` 完全两码事。

**回填后评估**：席位明细补齐（覆盖率 90.2%）后，A = C = D（81 天 / 105 票次）——
C、D 对放行量零增量，当前落地无收益。**暂不落地**，保留为兜底防御：

- 触发指标：重跑本脚本，表 2 中③④的 `null 缺失` 占比 **> 30%** 时建议启用；
- 落地方式（届时照此执行）：
  1. 在 `filterOne` 的 `check()` 分支做区分：字段 `=== null` → 标记 `skipped`、留日志、
     不计入 `unmet`；有值但不达标 → `unmet` 照常否决（对齐 `LOCKUP_RATIO`/`GAIN_60D` 范式）；
  2. **保留 `netOutflow` 降级不动**（既定风控，放开无实质改善）；
  3. 变更后重跑本脚本对比漏斗，并抽样核对**有席位数据的交易日**③④仍严格执行。
- 模拟口径（供落地校验）：C = 保留强制剔除+降级，三条准入各自 null 不否决；
  ④须两字段**都** null 才算缺失，只要一个有值仍要求 inst>0 或 north>0。

**不选 B**：旁路 `filterOne` 等于拆掉这一层龙虎资金风控，代价太大。
**不选 D**：单纯放开净流出降级，卡点依旧在席位准入缺失，无实质成交改善（A、D 均为 2 天）。

## 已知边界（不是 bug，别据此改策略）

- **必须走 `decodeArchive`**：裸 `data/archive.json` 里 `day.lhb` 编码在 `_sub` 中，
  直接读会得到 `lhb === undefined`，导致 `featuresOf` 取不到净买额、准入结论全错。
- **GLM 侧车档只有最新交易日的 `asOfDate`**（排雷黑名单/妖股逻辑/板块情绪），历史日按设计
  `fail-open` 不拦，故漏斗里 GLM 通过率恒为 100%——**不能解读成「GLM 无用」**。
- **regime 盖帽取当前档** `signals-latest`，非逐日重放历史 regime。
- 选股 `ctx` 复现 `paper_daily` step5（极寒分化扣分 / 主线对象 / `openGapFilterPct` /
  `seatsDetail` / `hotmoney`）；**改动生产 ctx 时须同步本脚本**，否则漏斗与线上不可比。
