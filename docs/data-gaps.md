# 数据缺口台账

> 归档序列（`data/archive.json`）里**缺失的交易日**记录。
>
> 为什么要有这份台账：**跨档审计是锚点式比对**（各档 vs 档案锚），天生看不见"序列中间
> 少一天"。一旦锚点跳到更新的交易日，缺口会被静默跨过去——`freshness` 落后数归零转绿、
> 审计转绿，**没有任何门禁会再提起它**。所以缺口必须在这里留痕，否则将来查序列时
> 发现少一天，只能重新考古一遍。

|---|---|---|---|---|---|

## 在册缺口

| 交易日 | 缺口范围 | 成因 | 上游原料状态 | 裁决 | 记录日 |

| 2026-10-09 | archive 整天、pain、离线五模块（宽度/主线/账本/亏钱效应/板块排行） | CI build 当日未产出（前序门禁红，build 整段 skipped，见 run #149） | **ztpool 涨停池 20261009 已入库 ✓**（69 只，与实测吻合）——不可补的那层没丢；`bt_kline` 本地缓存只到 09-30 | **接受缺口，默认不回补**（理由见下） | 2026-10-10 |

### 2026-10-09 裁决理由

1. **不紧急**：与 ztpool 不同，这一天的派生档**随时可补**——历史日线可由 BaoStock 按日期
   区间取得（`market_data.py` 的 `fetch_history_daily`，本机可达）。延后补不产生不可逆损失。
2. **补了也不进回测**：回填天必须打 `_backfill` 标记（否则就是"旧值顶替当日值"，
   正是 `534df3d` 双闸要根治的事故类型），而回测脚本**显式排除 `_backfill` 天**。
   故补录的净收益只剩"序列连续"，不提升指标/回测样本；成本是新编排代码 + 写生产档。
3. **收益/成本不支持**：仅为一天派生档写"按日期新增归档天"的编排，风险大于收益。

### 若将来要补（路径已备，随时可走）

1. 用 BaoStock 取 **2026-10-08** 全市场日 K → 走 `src/zt_rebuild.js` 重建 → 与档案里
   **真实的 10-08** 逐字段交叉验证（口径校验；`backfill_factors.mjs --validate` 同款机制）。
2. 验证通过 → 取 10-09 日 K → 写入 archive 该天并打 `_backfill` 标记 → `recalcAll` → 切片重建。
3. 跑全套：`node --test` + `check_contract.mjs` + `audit_data_caliber.mjs` 确认无回归。
4. **校验不通过就停下不补**（宁缺毋假）。

### 改判条件（满足任一即值得补）

- 在册缺口扩大到 **≥2 个交易日**（单点洞变成段，统计偏移不再是误差级别）
- 某个具体功能被确认因缺口出错（健康面板近 N 日统计、连板梯队链等）
- 需要这一天进入回测样本（那要先过上面的口径 validate，升级为真分，工程量更大）
